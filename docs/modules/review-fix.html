PR review and review fix

Workflow 3 writes one AI review comment per pull request. Workflow 3b lets a person write @ai on the PR so Copilot changes the PR branch and replies point by point.

On this page:PurposeComponentsWhich PRs are reviewed or fixed?Flow 1: reviewing a pull requestFlow 2: a review fixBusiness rules and edge casesDependencies

Purpose

PR review (ReviewPullRequestJob) gives a first-pass review before a human looks. It writes one comment per PR and updates it in place on each new head commit. It is advice and never blocks a merge. Review fix (FixReviewJob) answers a person's @ai comment on a PR: Copilot reads the latest review and the comments since the last fix, changes the code on the PR's own branch with the same stages and runner checks as Workflow 2, and the runner adds a commit, pushes it, and replies. The new head is then reviewed again.

Which PRs are reviewed or fixed?

Flow 1: reviewing a pull request

  1. context.md says whether the PR "was created by Workflow 2" (ai/issue-* branch) so the agent fills the stricter Spec check section (ContextBuilder.cs:53).
  2. A PR with no changed files, or whose files all match review.skipPaths (for example docs/**, **/*.md), is recorded as skipped and ends quietly (l.47-51).
  3. The review comment is updated in place. If the update fails (the comment was removed), a new comment is added (l.78-87).
  4. On failure OnFailed stores the failed head sha, so the same commit is not retried on every poll. The next commit is reviewed again (l.29-31).

Flow 2: a review fix

  1. The PR head is checked out as a local branch with the PR's branch name, and refs/pull/N/head is fetched too, so a fork PR gets a clear refusal instead of a git error (l.54-56).
  2. WhyNotFix refuses when the review fix limit is reached, when the PR comes from the default branch, or when origin/<branch> is missing or not at the PR head (JobPlanner.cs:135-148). The refusal is itself a reply, so the trigger is answered.
  3. review-fix.md has the latest REVIEW block, the last fix reply (so "undo 1" makes sense) and every human comment since that reply, oldest first (ContextBuilder.cs:90-117).
  4. Round 1 failure means nothing is pushed. Half-done work is not put on a PR someone is reviewing (l.74-76).
  5. The reply starts ## AI fix N - commit <sha>, K changed files on <branch>, then the agent's REPLY.md, the runner's checks and rounds (l.95-107).
  6. The reply carries the context-upto tag, and the local cursor is stored (l.117-121). A failure marks the trigger handled in OnFailed, with the text "Write a new comment with @ai to try again." (l.34-42).

Dependencies

  • Uses: IGitBucketClient, IWorkspace, IGitClient, ICopilotRunner, IStateStore, AgentSession (fix only), RunnerIdentity (the bot's login for scope).
  • Used by: JobWorker. The REVIEW comment is the input of every review fix. The linked analysis and SPEC come from Workflow 1.
  • Tests: FixReviewJobTests (15), ReviewAndSequenceJobTests (6), JobPlannerTests, ParserTests.
Warning Anyone who can comment on a PR in fix scope can make the agent change its code with @ai. The result is still a commit on the PR that a human reviews and merges, and the limits apply. Keep the ai label off PRs where that is not wanted (README.md, finding F3).
Gotcha A review fix uses two cursors on purpose. Trigger honours the local cursor, so a failed fix is not retried on every poll. RequestsSinceReply ignores it, so the requests of a failed fix still reach the next fix. The fix reads every comment since the last reply, so a person may write the points in several comments and put @ai in the last one.
