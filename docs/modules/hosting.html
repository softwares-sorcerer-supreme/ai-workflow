Poller, queue, worker

How work is found (Poller), stored (JobQueue) and run (JobWorker). Scheduling and lifetime only: no business decisions.

On this page:PurposeComponentsFlow 1: one poll of one repoFlow 2: the worker runs a jobBusiness rules and edge casesDependencies

Purpose

The Hosting/ folder turns the pure planner into a running service. Poller finds work, JobQueue remembers it across restarts, and JobWorker runs one job at a time with a timeout, a log folder, a cost row and a failure report. It makes no decisions about what to do. That belongs to Core (CLAUDE.md "Architecture").

Flow 1: one poll of one repo

  1. Two issue lists are merged: issues with the scope label, and issues assigned to the bot. The server may ignore the assignee filter, so the result is filtered again with IsAssignedTo (Poller.cs:54-57).
  2. seen holds the stored fingerprints. An issue is "changed" when its updated_at + labels differ (Poller.cs:59-62).
  3. Labels decide most jobs, so the first plan uses no comments (Poller.cs:68). Comments are fetched only when the plan needs them and the issue changed.
  4. If there is a job, it is enqueued. Nothing is remembered, so a job that fails without being able to tell anyone (VPN down) is planned again on the next poll (Poller.cs:12-15).
  5. If there is no job and the issue changed, the new fingerprint is stored. The issue is then not read again until it changes.
  6. PRs are listed only when review or fix is enabled. They have no fingerprint, so each in-scope PR costs one comment list per poll (Poller.cs:77-83).

Flow 2: the worker runs a job

  1. The job's Info.Timeout becomes both a deadline on JobRun (jobs read TimeLeft) and a CancelAfter on the token (JobWorker.cs:57-60).
  2. A cancellation caused by the host stopping is not a failure. The job stays running and is re-queued once at the next start (JobWorker.cs:76-80).
  3. The error text depends on the cause: JobFailedException message, "did not finish within N minutes", "A call to GitBucket timed out (VPN or server down?)", or TypeName: short message (JobWorker.cs:83-90).
  4. error.txt with the full exception is saved in the job's log folder and the failure comment points to that folder (JobWorker.cs:94, 114).

Business rules and edge cases

  • One pending job per key. A second request with the same key updates the payload and returns false (JobQueue.cs:26-31). A job may be pending while another with the same key runs. The second run re-reads GitBucket and does nothing if the first did the work.
  • One job at a time. Cost is predictable and the shared work/ clone is never used by two jobs at once.
  • PR failures add no label. The job itself remembers the failed commit (review) or marks the @ai comment handled (fix), so a PR is not retried on every poll (IJob.cs:31-34).
  • Per-repo isolation. A poll error in one repo is logged and the next repo is still polled. The catch ignores real shutdown but treats an HTTP timeout (also an OperationCanceledException) as an error (Poller.cs:40-47).
  • Log levels. A newly queued, non-routine job logs at Information. Routine and "already queued" go to Debug (Poller.cs:99-100).
  • Cost row: written for every non-quiet outcome and for failures: date, repo, number, workflow, seconds, result, detail (JobWorker.cs:133-135).

Gotcha The poller never writes to GitBucket. Only jobs and the worker's failure report do. If you add a write to the poller, dry-run would no longer be safe.
