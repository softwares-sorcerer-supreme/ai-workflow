Planning (Core)

The pure decision logic: which job does an issue need, which @ai comment is new, and which sub-issue starts next. No I/O, no DI, no async.

On this page:PurposeComponentsFlow 1: what does an issue need?Flow 2: which comment is new?Business rules and edge casesDependencies

Purpose

All "should this run?" rules live in one place: Core/JobPlanner.cs. The poller asks it to decide what to queue, and every job asks it again on fresh data before doing anything. That makes the planner the single source of truth, so duplicate or late jobs are harmless. Helpers decide which @ai comment is new (AtAiThread) and which sub-issue starts next (SubIssueSequencer). All of this is pure: it takes data in and returns a decision, so tests need no fakes (CLAUDE.md "Architecture").

Flow 1: what does an issue need?

  1. A closed issue, an issue with ai:failed, or one marked for the (unbuilt) cloud fallback is always skipped.
  2. ai-implement becomes an ImplementIssue job even if it will be refused. The job posts the reason and removes the label, so the human learns why (JobPlanner.cs:33-36).
  3. ai-breakdown works the same way. An issue that already has ai:parent is skipped as "already broken down".
  4. An ai:parent issue gets a routine sequencing job on every poll.
  5. Everything else is an analysis candidate. Without comments the planner cannot tell round 1 from a later round, so it answers "skip + NeedsComments" and the poller reads them (only if the issue changed).
  6. With comments, AtAiThread.Of(comments, Markers.Analysis, lastHandled) counts replies and finds the trigger. No reply yet means round 1. Otherwise a new @ai comment is needed.

Flow 2: which comment is new?

AtAiThread answers "is there an @ai comment nobody has answered yet?" without relying on the database. Each reply carries a hidden tag context-upto=N: the newest comment id the job had read when it started. A comment written while Copilot was running has an id above N, so it still counts as new.

  1. Constructor (AtAiThread.cs:21-30): the cursor of the last reply is its context-upto value, or its own id for an old reply without the tag. AnsweredUpTo = max(local cursor, reply cursor).
  2. Trigger (l.50-51): the newest non-bot comment with an id above AnsweredUpTo that mentions @ai.
  3. RequestsSinceReply (l.57): comments after the last reply, ignoring the local cursor on purpose. A failed fix marks its comment as handled, but its requests were never applied and must reach the next fix.
  4. Next(limit) (l.60): (Done + 1, Done >= limit).
  5. Reply(inner) (l.63): the block from Markers.Wrap plus the tag with ReadUpTo (the newest id in the comments passed in).

Dependencies

  • Uses: only Configuration/RunnerConfig.cs POCOs (RepoConfig, Workflows).
  • Used by: Hosting/Poller, Jobs/JobSupport, every job (for the WhyNot... checks and AtAiThread), SequenceSubIssuesJob (for SubIssueSequencer).
  • Tests: JobPlannerTests (23), AtAiThreadTests (13), SubIssueSequencerTests (6).
Gotcha PlanIssue is called twice by the poller: first with comments: null, then with the real comments (Poller.cs:68-71). The first call must never throw or assume comments exist, and a null comment list is a valid input that returns NeedsComments.
Warning Planner rules must stay the single source of "should this run" (CLAUDE.md). Do not add a check only inside a job. A job that disagrees with the planner will loop: the poller keeps queueing it and the job keeps saying "not needed".
Note Markers.Wrap replaces <!-- with &lt;!-- inside agent text, so agent output can never fake a block marker or a context-upto tag (Markers.cs:36-37).
