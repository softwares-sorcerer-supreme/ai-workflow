Architecture

A layered worker with a pure decision core. One pattern everywhere: Poll, Plan, Queue, Job. How a job runs, how failures are handled and how secrets are protected.

Architecture style

ai-runner is one project (src/AiRunner) with four layers. The folder is the namespace. The style is "pure core, impure shell": every decision and every piece of text parsing is a pure static function in Core/. Every side effect sits behind a small interface in Infrastructure/. Jobs/ glue them together, and Hosting/ only handles scheduling and lifetime (CLAUDE.md "Architecture").

The one pattern that repeats is Poll → Plan → Queue → Job:

  1. Poll: Poller reads issues and PRs from GitBucket (Hosting/Poller.cs:52-85). It never writes to GitBucket.
  2. Plan: JobPlanner turns labels and comments into "run job X" or "skip, because Y" (Core/JobPlanner.cs).
  3. Queue: JobQueue stores the job in SQLite and in a channel. There is at most one pending job per key (Hosting/JobQueue.cs:22-38).
  4. Job: JobWorker runs one job at a time. The job plans again on fresh data and quits quietly if the work is no longer needed (Jobs/JobSupport.cs:26-34).

Layers and dependencies

The rule "Hosting -> Jobs -> Infrastructure + Core" is written in CLAUDE.md. It is a convention, not enforced by the compiler (one project, no architecture test). In the code, Infrastructure files also using AiRunner.Core for the GitBucket models, which fits the rule.

Job lifecycle (the "request lifecycle")

ai-runner has no incoming HTTP requests. The equivalent of a request is a job. This is the full path from a poll tick to a finished job.

  1. The poll lists open issues with the scope label and open issues assigned to the runner's user, and merges them (Poller.cs:54-58).
  2. For each issue the poller plans with no comments first. Comments are fetched only when the plan says NeedsComments and the issue fingerprint changed (Poller.cs:68-71).
  3. If the plan has a job, queue.Enqueue adds it. If the same key is already pending, only the payload is updated (JobQueue.cs:26-31).
  4. JobWorker.RunOneAsync sets the job to running, starts a log folder, and links a timeout to the job's token (JobWorker.cs:49-60).
  5. The job runs. If the job says Quiet, its row and log folder are deleted. Otherwise the job is marked done and a cost row is written (JobWorker.cs:63-74).

Error handling

Note A job that is interrupted by shutdown stays running. At the next start JobQueue.Recover puts it back to pending once. After MaxAttempts = 2 it is marked failed and reported as "stopped twice" (JobQueue.cs:16, 64-83, JobWorker.cs:103-109).

Key design patterns

Pure core

All decisions and parsers are static, I/O-free functions. Easy to test with plain inputs. Core/JobPlanner.cs, Core/*Parser.cs.

Re-plan on every job

Each job calls JobPlanner again on fresh data, so duplicates and late jobs return NotNeeded. JobSupport.LoadIssueAsync.

State lives in GitBucket

Bot comments carry hidden markers, so deleting ai-runner.db is safe. BotComments, Markers, AtAiThread.

Fingerprint polling

GitBucket ignores since, so the poller stores updated_at + labels and reads comments only on change. GbExtensions.Fingerprint.

Interface seams

Every side effect has an interface (IGitBucketClient, ICopilotRunner, IGitClient, IProcessRunner, IWorkspace, IStateStore, ICostLog), so tests use fakes.

Job registry by DI

All jobs are registered as IJob; JobFactory builds a dictionary by JobType. The worker never switches on type. IJob.cs:50-56.

Strict output contract

Templates define what agents write. Parsers reject anything else, so a bad answer is never half-applied.

Agent stages + runner safety net

The agent verifies and reviews itself. The runner re-checks and sends one or more fix rounds. Jobs/AgentSession.cs.

Authentication and secret flow

Warning This is a guard rail, not a sandbox. The build, test and lint commands run code that the agent wrote, with the developer's OS rights. That code can read anything the developer can read, including the user-secrets file. The runner limits the damage (no tokens in the environment, a .git/config guard, a human reviews every PR) but does not isolate it (README.md "Security limits").
