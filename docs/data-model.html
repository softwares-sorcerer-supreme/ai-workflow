Where state lives

ai-runner keeps no database dependency for correctness (CLAUDE.md). The truth is in GitBucket: labels, comments and branches. The bot finds its own comments again by hidden markers. The SQLite file ai-runner.db only holds helper state (what the poller saw, which comment was handled, the job queue and the cost log). Deleting it is safe: the runner reads GitBucket again.

Files on disk

A job writes its inputs and results into logs/jobs/<yyyyMMdd-HHmmss>-<owner>-<repo>-<number>-<JobType>/ (JobLog.cs:44-48). The folder is created on the first write. A job that writes nothing leaves nothing.

FileWritten by
job.logJobRun.Info: every run.Info(...) line

round-N-copilot-stdout.txt, -stderr.txt, round-N-transcript.mdImplement and fix runs (AgentSession)
round-N-check-M.txt, setup.txt, fix-N.mdCommand output and the input of fix round N

error.txtFull exception text of a failed job (JobWorker.cs:94)

The working clone work/<owner>/<name> also holds runner files that are never committed. They are listed in .git/info/exclude: .ai-workflow/, context.md, plan.md, PR_BODY.md, fix.md, diff.patch, changed-files.txt, review-fix.md, REPLY.md (Workspace.cs:28-30).

Migrations, stored procedures, views

  • Migrations: none. The schema is created in the SqliteStateStore constructor with CREATE TABLE IF NOT EXISTS (SqliteStateStore.cs:63-80). A later change to a table would not change an existing file. See Findings.
  • To reset: delete ai-runner.db (and its -journal file). *.db is git-ignored.
  • Stored procedures, views, triggers: none. All SQL is inline with named parameters (no string concatenation of values).
  • Connections: one connection is opened per call (pooling on). The multi-statement AddJob returns last_insert_rowid() from the same command (SqliteStateStore.cs:123-130).
